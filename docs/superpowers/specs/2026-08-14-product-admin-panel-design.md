# Product Admin Panel Design

Date: 2026-08-14
Status: Approved by user ("ok")

## Context

Product data for all four storefronts (camaroom-web/Cameroon, Nigeria-website,
Sudan-website, Mali-website) lives in each repo's own
`assets/data/products.js` — a hand-editable JS file (`const PRODUCTS = [...]`)
originally generated by `scripts/build_products.py` from a one-time catalog
import. Adding, editing, or hiding a product today means directly editing
that file and the matching image files in `assets/products/`, then
committing and pushing — documented for a technical editor in
`docs/product-data-guide.md`.

The user wants a real admin panel: a password-protected web page where
someone can add/edit/hide/delete products and drag in photos, without
touching code or git directly. The person operating it is the user or
another technically-comfortable person at the company — not local country
staff, who have no GitHub accounts and were described as needing something
"simple" (a concern already satisfied by this design: end users never see
GitHub, only a login + form).

The backend/ directory already has a working, deployed pattern for exactly
this shape of tool: `camaroom-cart-backend` (Cloudflare Worker + D1),
`src/auth.js` (password + HMAC-signed cookie session), and
`src/admin_pages.js` (server-rendered HTML admin pages — `/admin/shipments`,
`/admin/inventory` — with inline vanilla JS calling a JSON API). This design
reuses that auth pattern but does not extend `camaroom-cart-backend` itself,
since that Worker's D1 database is scoped to Cameroon's orders/inventory —
product-catalog editing is a different concern and two of the four sites
(Nigeria, Sudan) have no backend deployed at all today.

## Goals

- One admin panel covering all four sites; after logging in, pick which
  country's catalog to work on.
- Add, edit, hide/show (existing `hidden:true` convention — see
  2026-08-14's "hide 35 products" change), and delete products.
- Drag-and-drop photo upload as part of add/edit — no manual git/GitHub
  step for the user.
- Batch-import a CSV of product text fields for bulk catalog entry.
- Saving a product commits directly to that site's GitHub repo; the user
  confirmed a 30–60s GitHub Pages redeploy delay before it's live is fine.
- Simple UI: dropdowns instead of typed category codes, drag-and-drop image
  area, clear save confirmation — operable without reading code.

## Non-goals

- Instant (sub-second) publish. Rejected in favor of staying git-backed —
  see "Alternatives considered."
- Local-staff-facing UI/accounts. Only the user (or another technical
  person at the company) logs in; no per-staff accounts, no multi-language
  UI beyond clear English labels.
- Automatic image resizing/compression server-side. Handled client-side
  (browser canvas) before upload — see "Image handling."
- Deploying new Cloudflare Workers/D1 databases for Nigeria/Sudan. This
  design needs none — see Architecture.
- Real-time collaborative editing / conflict resolution beyond what's
  described in "Error handling."
- Migrating `products.js` to a different file format (e.g. JSON). It stays
  exactly the format `build_products.py` already produces — see "Products.js
  edit strategy."

## Alternatives considered

1. **This design (chosen): one stateless Worker, GitHub Contents API,
   git stays the source of truth.** No new database. Storefronts remain
   fully static (doesn't reintroduce the load-time regression just fixed).
   Works identically for all 4 repos regardless of whether they have a cart
   backend. Trade-off: ~30-60s GitHub Pages redeploy delay after saving,
   accepted by the user.
2. **D1-backed catalog, storefront fetches products at runtime.** Instant
   publish, but requires deploying Workers+D1 for Nigeria/Sudan from
   scratch, needs an object store (R2) for images, and turns each page load
   into a live API dependency — directly working against the page-speed
   work done earlier this session. Rejected.
3. **Hybrid: D1 staging + explicit "Publish" step that regenerates and
   commits products.js.** Best of both, but two systems to keep in sync for
   a catalog this size — more moving parts than the problem justifies right
   now (YAGNI). Rejected.

## Architecture

**New standalone Cloudflare Worker, `camaroom-admin`,** in a new top-level
directory `admin-backend/` (sibling to `backend/` in camaroom-web — this
repo stays the one place all four sites' shared tooling lives, matching
where `scripts/generate_country_site.py` already lives). No D1 database, no
bindings other than environment secrets. Two secrets:

- `ADMIN_PASSWORD` — reused pattern from `backend/src/auth.js` (copy the
  module as-is; it has no D1 dependency).
- `GITHUB_TOKEN` — a GitHub Personal Access Token (fine-grained, scoped to
  exactly these 4 repos, Contents: Read and write permission) that the user
  generates themselves and provides. **User action item, not something
  Claude can create.**

A config module maps country → repo:

```js
// admin-backend/src/repos.js
export const COUNTRY_REPOS = {
  cameroon: { owner: 'zhixuanlucasfeng-cmyk', repo: 'camaroom-web',      name_en: 'Cameroon' },
  nigeria:  { owner: 'zhixuanlucasfeng-cmyk', repo: 'Nigeria-website',   name_en: 'Nigeria'  },
  sudan:    { owner: 'zhixuanlucasfeng-cmyk', repo: 'Sudan-website',     name_en: 'Sudan'    },
  mali:     { owner: 'zhixuanlucasfeng-cmyk', repo: 'Mali-website',      name_en: 'Mali'     },
};
```

All GitHub calls go through the Contents API
(`GET/PUT /repos/{owner}/{repo}/contents/{path}`), which handles both
reading a file (with its blob `sha`, required for updates) and writing one
(create or update, given the previous `sha` to avoid clobbering concurrent
edits — see "Error handling").

## Routes

Server-rendered admin pages (HTML + inline vanilla JS, same style as
`admin_pages.js`), all requiring the `isAuthenticated` cookie check:

| Route | Purpose |
|---|---|
| `GET /admin` | Login page (if not authenticated) or redirect to `/admin/products` |
| `POST /admin/login` | Same as existing pattern: checks password, sets session cookie |
| `GET /admin/products?country=X` | Product list for country X: thumbnail, name, cat, price, hidden badge, edit/hide/delete actions, "+ Add product", "Import CSV" |
| `GET /admin/products/new?country=X` | Add-product form |
| `GET /admin/products/:id/edit?country=X` | Edit-product form, pre-filled |
| `GET /admin/products/import?country=X` | CSV upload page |

JSON API (also cookie-authenticated):

| Route | Purpose |
|---|---|
| `GET /api/admin/products?country=X` | List products (reads + parses that repo's products.js) |
| `POST /api/admin/products?country=X` | Create a product |
| `PUT /api/admin/products/:id?country=X` | Update a product |
| `POST /api/admin/products/:id/toggle-hidden?country=X` | Flip `hidden` |
| `DELETE /api/admin/products/:id?country=X` | Remove a product entirely |
| `POST /api/admin/products/import?country=X` | Bulk-create from parsed CSV rows |

## Products.js edit strategy

Each product is one line (see `build_products.py`'s `render_products_js`):

```js
{id:"SP-005", cat:"panel", img:"SP-005.jpg", gallery:["SP-005.jpg"], name:"RT6S-M", price:0, desc:{...}, specs:{...}, warranty:null},
```

The Worker never fully re-parses/re-serializes the file. Instead:

- **Read (for the list page):** fetch the file text, extract the array
  contents, and `Function('return [' + arrayBody + ']')()` to get real JS
  objects to render — safe here because the input is our own repo's file,
  not user-supplied at this point.
- **Create:** build one new line with the same field order/format as
  `build_products.py` (object keys unquoted, values through
  `JSON.stringify` — which already produces the right quoted-string/array/
  object syntax for each value), insert it just before the closing `];`.
- **Update:** regex-match the line whose `id:"THAT_ID"` matches, replace
  the whole line with a freshly-built one (same approach as `create`,
  preserving fields not shown in the edit form, like `warranty`).
- **Toggle hidden:** the narrow, already-proven approach from this
  session's `hide_bad_products.py` — regex-insert/remove `, hidden:true`
  right after that product's `cat:"..."` segment.
- **Delete:** regex-match and remove that product's entire line.

This keeps every admin-driven commit a minimal, readable diff (one line
changed), consistent with how this file has been hand-edited all session,
and avoids the risk of a full-file reserialization drifting from
`build_products.py`'s exact formatting.

## Product form fields

- Category — dropdown (`panel`, `battery`, `inverter`, `ess`, `controller`,
  `pump`, `fridge`, `light`, `fan`, `kit`), labelled with the same
  human-readable names the storefront uses (`catLabel()` in index.html).
- Name, Price (0 = "Contact for price", matches existing convention).
- Description — English and French text fields (Arabic is Sudan-only and
  currently unused for `desc` — out of scope, matches current site
  behavior where Sudan falls back to English for `desc`).
- Specs — repeatable key/value rows ("+ Add spec"), free-form, no fixed
  count (matches `docs/product-data-guide.md`).
- Photos — drag-and-drop, multiple files, becomes the `gallery` array;
  first photo is also `img`.

ID is auto-generated on create: `{PREFIX}-{next number}` where prefix comes
from category, matching the SKU prefixes already used in `products.js`:
`SP` (panel), `BAT` (battery), `INV` (inverter), `ESS` (ess), `CTRL`
(controller), `OTH` (pump, fridge, light, fan, and kit all share this
prefix today — they're sub-classifications of one original source
category, not separately numbered). The number is one past the highest
existing number for that prefix in that country's file.

## Image handling

Resizing/compression happens **client-side**, in the browser, before
upload: a small canvas-based helper resizes to a 1000px cap on the long
side and re-encodes as JPEG (quality ~80) — the same target this session's
manual compression pass used. This means the Worker only ever receives
already-reasonably-sized files, and needs no image-processing capability
itself (Workers don't have one readily available without adding a paid
Images binding, which this design avoids). The Worker base64-encodes each
resized file and PUTs it to `assets/products/{id}-{n}.jpg` via the Contents
API.

## CSV import

Text-only for v1 (per "Non-goals" — no bundled images in the same import).
Columns: `cat, name, price, desc_en, desc_fr, specs` (specs as a single
`key=value;key=value` cell). Each row becomes a product with a
placeholder/no image (shows the existing icon fallback until someone edits
it in to add photos) — this is an explicit, visible "needs photos" state,
not a silent gap, consistent with this session's "35 hidden products" fix
having made wrong-vs-missing images a first-class, visible problem to fix
rather than something that quietly ships wrong.

## Error handling

- **Stale write (two saves racing):** Contents API update requires the
  file's current `sha`; if it's changed since the form loaded, GitHub
  returns 409 and the Worker surfaces "Someone else changed this file —
  reload and try again" rather than silently overwriting.
- **GitHub API failure** (network, rate limit, bad token): surfaced as a
  clear error banner on the form, input preserved so the user doesn't
  retype everything.
- **Validation:** category must be one of the known set; price must be a
  non-negative integer; name and at least one spec required; server-side
  validation mirrors client-side (never trust the browser alone).
- **Duplicate ID:** create always auto-generates, so this can only happen
  on CSV import collision — skip the row and report which ones failed,
  don't abort the whole batch.

## Testing

`admin-backend/` gets its own `vitest` setup (copy config from
`backend/vitest.config.js`). Unit tests cover: the line-serialization
format (round-trip a product object through it and confirm the output
matches `build_products.py`'s format), ID auto-generation, CSV parsing,
and the hidden-toggle regex — all pure functions, GitHub API calls mocked
at the fetch layer. No integration test against real GitHub (would require
a live token and pollute a real repo); manual smoke-test against a scratch
repo before first real use is called out as a plan step instead.

## Deployment

- `wrangler.toml` for `camaroom-admin`, no `[[d1_databases]]` block.
- User runs `wrangler secret put ADMIN_PASSWORD` and
  `wrangler secret put GITHUB_TOKEN` once, after generating the GitHub
  token (user action item, called out above).
- Worker gets its own `*.workers.dev` URL (or a custom subdomain if the
  user wants one later — out of scope for v1).
